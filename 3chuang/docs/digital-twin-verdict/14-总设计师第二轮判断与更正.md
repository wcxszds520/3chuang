## 第 1 节　我先认错：它纠正我的两条，我核实后确认我错了

### 1.1 「商业软件都支持异形」——我错了

我在 `13` 号文档里写"异形有标准答案：最小外接长方体"，并把它列为"我们缺什么"的第一条。

**EasyCargo 官方帮助页原文**（我已实测抓取）：

> "Currently, you can **only** plan the loading of **cuboid and rectangular shapes** with EasyCargo. Unfortunately, **cylindrical shapes/pipes/other round articles are not supported yet**. We have this on our list of most wanted features... However, it is rather a **long-term goal**.
> Other types of shapes are **not planned for the near future**. For example, we don't plan to add triangular shapes as **the calculation would become too complex**."

**EasyCargo —— 我们最主要对标的竞品 —— 明确不支持圆柱。**

**我错在哪**：我的依据是 LoadOptimizer FAQ、JustLoad.it、thecbmcalc.com。这些是**小型在线工具与博客**，不是主流商业产品。**我把小工具的"外接框建议"当成了行业标准做法。**

**而且它的理由比我的结论更有信息量**："the calculation would become **too complex**"。这说明**异形不是"加个外接框就解决"的问题**——连成熟商业软件都主动选择不做。

### 1.2 「分组是免费的前处理」——我也错了

我在 `13` 号写：*"多批次/多目的地应作为分组键在搜索之前处理，而不是作为约束进入搜索"*。

**EasyCargo 官方帮助页原文**（我已实测抓取）：

> "If you want to prevent group overlap, use the **'No stacking of priority groups allowed'** or the **'Split of priority groups with a invisible wall'** command... The latter setting also **divides the cargo space into separate sections**... **Both of these settings will slightly reduce the usable cargo space**, same as with the **'do not stack'** constraint.
> The last function is **Ignore separation into priority groups**. With this function, calculation will be done with **no limitations by groups**..."

**这直接推翻我的论断，三点证据：**
1. 分组隔离（禁叠 / 虚拟墙）**会减少可用空间** —— 不是免费的
2. 存在"**忽略分组**"模式 —— 说明分组是**一种可选约束**，不是前处理标签
3. 默认是"遵循分组顺序"，但**允许组间堆叠** —— 说明"顺序"与"隔离"是两种不同强度的东西

**对方的表述才是准确的**：

> "在搜索前确定分组的业务含义，再把确实需要执行的关系交给搜索器；**只有纯统计标签，才不影响几何求解**。"

**我服这条。** 我把"分组"当成了"标签"，但它是**约束的一种表达方式**。这个区分会决定代码写对还是写错。

### 1.3 另外三条过强结论，我也接受更正

| 我的说法 | 问题 | 更正 |
|---|---|---|
| "没有任何商业或学术实现求解最优" | 过强。存在精确分支定界研究（Martello/Pisinger/Vigo 2000 + 2005 勘误） | 改为"大规模一般用启发式，但小规模精确解、构造可行解与可靠上下界都可作质量尺子" |
| "算法 0 分，所以核心修复可后置" | 框架太粗。评分表同时要求"逻辑无明显错误、操作方便、模块使用流畅、无明显 Bug" | 影响结果正确性与响应时间的缺陷必须同步修 |
| 用上一届 9 月日期倒推"只剩 9 天" | 我在用上届时间线做当前决策 | 应核实本届真实截止；**核实不到就问用户** |

### 1.4 还有三条技术细节，它说得对而我没想到

1. **外包络顶面 ≠ 实际支撑面**：卧式圆柱的包络有水平顶面，但物体本身不是平顶。若碰撞用包络、支撑检查也直接用包络顶面，会**允许箱子悬在圆柱两侧的空白区域上**。
2. **L 形不能拆成两件独立货**：可以表示为多个局部盒体的并集，但必须**共享同一 root 变换、物理 ID 和总数量**。我在 `13` 号给了"拆两件或整体外接框"两个选项——**"拆两件"是错的**。
3. **体积口径不能混**：圆柱几何体积 `πr²h` 与外接包络体积 `(2r)²h` 必须分别保存。包络密铺到 100% 时，圆柱实体体积占比仍是 **π/4 ≈ 78.54%**，不能把"包络利用率 100%"标成"货物体积利用率 100%"。

## 第 2 节　它比我强的地方（设计精度）

| 项 | 它的设计 | 我的对应 |
|---|---|---|
| **关系分类** | **9 类**：`INFO_ONLY` / `SAME_CONTAINER` / `ALL_OR_NONE` / `RATIO` / `PREFER_NEAR` / `UNLOAD_PRECEDENCE` / `FORBID_STACK_BETWEEN` / `SEPARATE_REGION` / `INCOMPATIBLE` | 我只说"分组键"，粒度粗一个数量级 |
| **规则二维拆分** | `requirement`（MUST / PREFERENCE / INFORMATION）× `evaluationStages`（PREFLIGHT / CANDIDATE / PARTIAL_BOUND / FINAL / DISPATCH） | 我的 enforcement 四类（候选/终态/目标/申报）**混了两个维度** —— 一条承压硬条件可以同时参与候选判断与最终复核，我的一维分类无法表达 |
| **规划意图** | `FIXED_ONE` / `CHOOSE_ONE` / `ALLOCATE_ALL` | 我只说"input minimization"，没有把"固定一个柜"和"允许多柜全装"分开 |
| **几何分层** | 源物体几何 / solver collision proxy / **实际支撑承压面** / 操作固定预留 / 纯视觉模型 —— **五层分开** | 我没分 |
| **eta 三策略** | `IGNORE_FOR_PACKING` / `READY_BY_CUTOFF` / `ORDERED_SERVICE` | 我的断言"eta 非空时装载量不应低于为空时"**无条件不成立** —— 若装柜截止在明天，后天才到的货本来就不该参加 |
| **多柜反馈** | 选柜与分配**双向反馈迭代** | 我画成了单向（先选死组合再分配） |
| **关系与顺序** | "先装完 A 再装 B"**不自动证明卸货时不会被挡住**，需判断上压关系、门口方向、取出路径 | 我没意识到 |

**两个逻辑上的额外收获：**
- **"同一订单别拆到不同柜" ≠ "把订单内所有件拼成一个巨大刚体"** —— 这个区分很关键
- **"体积加起来装得下"不证明各件真的能分配并摆进去** —— 总重总体积只是必要条件筛选

**它还承认了我对它的批评**（"只强调防错，没规定没发现缺陷时下一步怎样改"），并在第 10 节补了支线。**这是它自我修正，我认可。**

## 第 3 节　它仍有的三个缺口

### 缺口一：否定了我的时间假设，但没给替代方案

它说"不能用上一届日期推当前窗口"——**这条对**。但它**只否定，不给替代**。用户仍需要一个执行节奏。

**正确的处理不是任一方假设，而是去问用户要本届真实截止日期。** 这是双方都不该假设、而用户自己知道的信息。

### 缺口二：第一批执行包仍是"修复"，不是"搜索改造"

它批评我"防御强推进弱"。但它自己的第一批（第 10 节）是：
- A：复现 ETA + 新增显式 policy
- B：deadline / 取消 / 最佳解保护
- C：视觉小补丁

**第 7 节那 8 条搜索设计（块/墙构造、极点构造、可累计局部重排）被推到了"第二批"。**

这个顺序本身有道理（先修语义再改搜索），但**它的第一批和我批评它的"只做检查"相比，投入产出上差别不大——都是从"输入语义 + 执行控制"起步。** 这一点它没有自我承认。

### 缺口三：没给「现有模块可复用清单」

它主张"复用当前有效模块，不再堆修复器"。但**没列出现有模块和各自可用性**。

而事实是：`RECOVERED` 的 `services/packing/` 有 **31 个模块**，其中已确认存在：
- `SourceBenchmarkSolver.js` — 算法名 `SOURCE_MAXIMAL_SPACE_PORTFOLIO`，已实现**最大空间 + 多策略组合**
- `CommerceWallPacker.js` / `CommerceColumnPacker.js` / `CommerceDoorReservePacker.js` / `CommerceRepack.js` — **墙式/柱式装箱器**
- `DenseColumnCandidate.js` / `GeometryPackingCandidate.js` / `OrientationConstraint.js`
- `BackWallSolverPass.js` / `ExactLayoutMetrics.js`
- 另有 `PlatformValidator` / `PlanMetrics` / `SecuringAnalyzer` / `CanonicalOperationFeasibility` 等

**"哪些复用、哪些废弃"是第一批执行包最需要的输入，而这份决策文件没给。** 这是我可以补上的。

## 第 5 节　第一批（等我拿到上面三样，立刻开工）

**范围**（合并它的第 10 节 + 我要求补的第 ③ 项）：
