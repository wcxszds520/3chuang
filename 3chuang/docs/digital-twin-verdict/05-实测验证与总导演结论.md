### ❌ 判定"过时 / 明显过重"的部分

**四份报告（含我自己的初版）共同高估了"视觉效果差"的程度。** 这是本次实测最重要的修正：

我实际打开的是**当前代码**（不是 6 月那张 `round2-stage-4-twin-3d.png`），看到的是：

- **落地页 hero**：工业蓝集装箱，波纹墙、锁杆、门附件齐全；货物是带木纹的板条箱、印刷标签纸箱、白色 IBC 吨罐、蓝色油桶、缠绕膜托盘——**这是一张合格的产品级渲染**，光影干净，有落地投影，还带三处标注引线。
- **孪生总览**：42 件货物辨识清楚，木箱纹理、标签、青色设备箱都可读；箱体半透明是为了"看得见内部"，属于功能取舍而非错误。
- **顶视 / 门侧**：构图合理，货物可辨。

所以：
- 报告 02 的"像在摄影棚里拍积木"——**过重**。真实情况是"灯光偏平、缺少方向性"。
- 报告 01 的"3D 玩具感扣 3 分"——**过重**。它没有看到当前版本。
- 报告 01/03/04 都是基于旧截图与源码推断，**没有实际打开过页面**，这是它们共同的方法论缺陷。

**真实且仍然成立的问题只剩三条**：① 光照偏平（影棚环境 + 低半球光）；② 装配与剖切视图的相机构图；③ 容器/工人/地牛未批处理导致的 1,000+ 冗余 draw call。

## 四、总导演决策：接下来的修改方案

### 定级原则

优先级 = **观感提升 × 收益确定性 ÷ 风险**。凡是不改变已验证通过的逻辑、只调整表现层的，排前面；凡是要动资产或引擎的，一律后置并隔离分支。

### P0-A　光照校正（半天，零风险，最高确定性）

实测证实光照参数与报告 02 的描述完全一致，因此它的方案可以照抄。但**建议先做 A/B 对比再定稿**，因为当前画面并不难看——目标是"更立体"，不是"推倒重来"。

```
environmentIntensity  0.48 → 0.85
HemisphereLight       0.32 → 0.95   地面色 #252321 → #3d3a34
toneMappingExposure   1.04 → 1.00
Fog                   18,48 → 30,80
rim (DirectionalLight 2.1) → 1.5
```

改完后必须与当前版本并排截图对比，确认"更好"而不是"更亮"。

### P0-B　补三处静态合并（1 天，低风险，收益最大）

容器 215 个 mesh 未合并，是当前最大单点浪费。照叉车的成例（453→36）补调用：

- `TwinScene.jsx:475` 容器 onReady → 合并静态件，保留 `door_left_pivot` / `door_right_pivot`
- `TwinScene.jsx:533` 工人 onReady → 合并静态件，保留 `rig` 全部枢轴
- `TwinScene.jsx:467` 地牛 onReady → 合并静态件，保留 `jack_wheel_*`

**验收标准**：`mount.dataset.containerHeroMeshCount` 从 215 降到 ≤30；静态 draw call 从 937 降到 ≤450；回放峰值从 ~2,000 降到 ≤1,100。同时确认全部枢轴仍存活、货叉/门/手臂仍能动。

### P0-C　相机构图（1 天，零风险）

实测确认的问题，按视图分治：

- **剖切视图**：主体只占画面约 1/3，上下留白过多 → 收紧 `computeCameraFrame` 的 margin
- **回放视图**：容器左侧被裁、人物偏小 → 抬高 `controls.target.y`，底部预留播放栏高度
- **跟随视图**：`跟随作业` 按钮在 `MOVE_TO_CARGO` 阶段点击未生效，需要确认是否被阶段门控（若是设计如此则界面应给出禁用态提示）

### P1-A　材质与贴合（1 天）

- `1,204` 个唯一材质偏多，是 draw call 与状态切换的来源之一，配合 P0-B 一并收敛
- 把已存在的 `cargoSurfaceTextures().bumpMap` 接到放置件（`:966-977` 当前只设了 `map`）
- 修正 `:593` 的 `bumpScale = .001` 死值
- 统一 `anisotropy` 到 8–16

### P1-B　画质档真正差异化（1 天）

实测：流畅档与标准档只差 9 个 draw call，**档位形同虚设**。重做：

| | 流畅 | 标准 | 极致 |
|---|---|---|---|
| pixelRatio | 1.0 | 1.25 | 1.5 |
| 货物 LOD | 合并空心箱、关 edges | 全量 + edges | 全量 + edges + 细节件 |
| GTAO | 关 | 0.5 分辨率 × 8 | 0.75 分辨率 × 12 |
| 环境反射 | envMapIntensity 0 | 0.8 | 1.0 |
| 线框/证据叠加 | 关 | 仅当前件 | 全开 |

**验收**：流畅档 draw call 必须显著低于标准档（目标 ≤ 标准档的 60%）。

### P1-C　资产瘦身与压缩闸门（2–3 天，需改资产，独立分支）

只在 P0 全部稳定后做。`gltfpack -cc -tc -kn -km`，**`-kn` 是硬要求**（枢轴靠节点名驱动，实测已确认 `forklift_carriage` / `door_*_pivot` / `worker_*_pivot` / `jack_wheel_*` 全部依赖节点名）。用 `tools/glb-inspect.js` 挂 CI 闸门，并加一条命名节点存活检查。

### P2　暂缓项（明确不做或后置）

| 项目 | 决定 | 理由 |
|---|---|---|
| 升级 three r179 → r185 | **后置到全部 P0/P1 稳定后，独立分支** | 改动面大且与当前问题无因果关系；pmndrs `postprocessing` 与内置 `EffectComposer` 混用是主要阻塞点 |
| 上 WebGPU | **暂缓** | 当前瓶颈是 draw call 与材质数，不是 API 上限 |
| Tripo 替代建模 | **仅用于 IBC 桶 / 油桶 / 堆场环境等 hero 件** | 实测确认关节资产全部依赖命名枢轴，Tripo 不保留层级枢轴 |
| 重建程序化资产 | **不做** | 实测确认全部资产来自 GLB，程序化仅是兜底 |

### 业务侧（与 3D 解耦，可并行）

1. `cargo.js:97` + `scenarioTemplates.js:17` 的重货阈值改为**积载密度或需机械作业**判据，而不是 `weight >= 20`
2. `handlingMethod = forklift` 时强制 `forkEntry` 非 `NOT_APPLICABLE`
3. VGM 补录补上申报人 / 核实人 / 回执，并明确"仅本地记录、未向承运人或码头发送"

## 五、一句话结论

> 四份报告**方向对、数字错、且共同高估了画面的糟糕程度**——因为它们都只看源码和旧截图，没有真正打开项目。
>
> 实测下来，这个项目的 3D **已经到产品级**（落地页 hero 就是证据），真正剩下的问题只有三个：**光照偏平、装配视图构图弱、容器没做静态合并**。
>
> 所以接下来的动作不是"抢救"，是**收尾**：改 5 个光照数、补 3 处静态合并、重排 3 个相机、让画质档真正起作用。**不要升级引擎，不要重建资产，不要换技术栈。**
