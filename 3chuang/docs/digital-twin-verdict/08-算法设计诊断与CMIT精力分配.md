## 第 1 节　为什么 25 版始终不满意：这是结构问题，不是精度问题

### 1.1 证据：版本演进的方向错了

查看 `services/HybridConstraintPackingSolverV25.js` 的 import 段（第 4–22 行）：

```js
const HybridConstraintPackingSolverV2  = require('./HybridConstraintPackingSolverV2');
const HybridConstraintPackingSolverV23 = require('./HybridConstraintPackingSolverV23');
const PlanValidator = require('./packing/PlanValidator');
const { centerPlan, applyDerivedTeamManual } = require('./HybridConstraintPackingSolverV24');
const { analyzeLayoutQuality } = require('./packing/LayoutQualityAnalyzer');
const { analyzeVoidJustification } = require('./packing/VoidJustificationAnalyzer');
const { attemptVoidDrivenLocalRepair } = require('./packing/VoidDrivenLocalRepair');
const { attemptLoadBalanceAwareLocalRepair } = require('./packing/LoadBalanceAwareLocalRepair');
const { compactDeepEnd } = require('./packing/EndGapCompaction');
const { attemptWallOrderRepair } = require('./packing/WallOrderRepair');
const { generateLaneStackCandidates } = require('./packing/LaneStackRepacking');
const FloorExtremePointCandidate = require('./packing/FloorExtremePointCandidate');
const { analyzeSecuring } = require('./packing/SecuringAnalyzer');
const { analyzeOperationFeasibility, canonicalLoadingSequence } = require('./packing/CanonicalOperationFeasibility');
const { analyzeLoadDistribution } = require('./realworld/LoadDistributionAnalyzer');
const { validatePortAccessibility } = require('./realworld/PortAccessibilityValidator');
```

**14 个"修复器"和"分析器"被挂在同一个求解器上。**

这说明版本演进的方式是：**V25 不是一个新算法，而是"跑 V23 出基础方案 → 再套 5~6 种局部修复 → 凑成候选池取前 8 个"。**

### 1.2 搜索宽度从未被提升过

| 参数 | 实际值 | 出处 | 评价 |
|---|---:|---|---|
| `beamWidth` | **4** | `HybridConstraintPackingSolverV2.js:28` | 每步只保留 **4 条**路径 |
| `candidateLimit` | 10 | 同上 `:30` | — |
| `maximumCandidates` | **8** | `V24.js:20`、`V25.js:32` | 全局候选池上限 **8 个解** |
| `FloorExtremePointCandidate.maximumInstances` | **9** | `V25.js:73` | 只处理 **9 个实例** |
| `maximumLocalRepairItems` | 30 | `solverPolicy.v25` | 修复只动 **30 件** |

**25 个版本过去，搜索宽度是 4 和 8。** 对 600 件的实例，"beam width = 4"意味着第二步就把 99% 的可能解剪掉了。

一个对照：`FloorExtremePointCandidate` 用了 `beamWidth: 512`（宽得多），但它被 `maximumInstances: 9` 限制住，只对极小规模生效。**真正需要宽度的地方窄，不需要的地方宽。**

### 1.3 同时，约束在不断叠加

从版本号能读出叠加史：V21 guardrail → V23 lane repacking → V24 candidates → V25 void repair + load balance repair + wall order repair + end gap compaction。

**每一次"改进"都是在外面再套一层约束或修复，没有一次是改搜索范式。**

### 1.4 结果：可行域指数收缩 → 装载率崩塌

实测（V25 跑 5 套内置数据集）：

| 数据集 / 箱型 | 件数 | 货理论占箱容 | **实际装入率** | 耗时 |
|---|---:|---:|---:|---:|
| **largeBatch / 40HQ** | **600** | **39.80%** | **22.8%（137/600）** | **180s** |
| mediumBatch / 20GP | 270 | 44.36% | **59.3%** | 23s |
| cixiAppliances / 40HQ | 587 | 57.00% | 78.4% | 120s |
| mixedCargo / 20GP | 69 | 57.55% | 94.2% | 3.6s |
| smallBatch / 20GP | 30 | 7.37% | 100% | 1.1s |

**largeBatch 的 600 件是什么货？**（`config/demo-cargo-templates.js:118-212`）

| SKU | 尺寸 | 数量 | 可堆叠 | 最大层数 |
|---|---|---:|---|---:|
| 纺织品箱 | 600×400×400 | 180 | 是 | 4 |
| 鞋盒 | 350×250×150 | 200 | 是 | 8 |
| 塑料制品 | 500×400×300 | 120 | 是 | 5 |
| 玩具箱 | 400×300×250 | 80 | 是 | 6 |
| 五金工具 | 450×350×280 | 20 | 是 | 4 |

**全是小规格、规整、可堆叠、可旋转的箱子，总体积 30.39 m³，装了 76.35 m³ 的柜子。**

在运筹学里这是**最理想的一类算例**。任何合格的 3D 装箱实现都能把它装到 85% 以上的体积利用率——也就是几乎全部 600 件。

**实际装入 137 件。这不是几何限制，不是货量不足，是算法失效。**

数据集描述写的是"3港口LIFO高密度"。**港序约束 + 极窄搜索宽度 = 组合爆炸导致的搜索失败。**

### 1.5 一句话诊断

> **你把 25 个版本都用来"给同一个启发式打补丁"，从来没有换过搜索范式。**
> 每加一层约束，可行域指数收缩；为救装载率再加修复；修复破坏不变量，再加校验——
> 这就是"迭代 25 版仍不满意"的完整机制。

## 第 2 节　正确做法：约束分三层，而不是一层

**这是整份文档最重要的一节。**

现在的实现把**所有**约束一律当"通过/不通过的门禁"（hard gate）。后果是可行域被压到近似空集——因为引导性条款（重心 5%/10%、港序）被当成了红线。

### 2.1 三层模型

| 层 | 性质 | 处理方式 | 典型项 |
|---|---|---|---|
| **H 硬约束** | 物理/几何上**绝不可能违反** | **在候选生成时就剪枝**，永远不产生违例候选 | 碰撞不重叠、箱内包络、堆叠承载不超限、易碎件不得受压、危险品隔离、单柜限重与轴载 |
| **S 软目标** | 业务偏好，**允许不满足但要付出代价** | 进入**候选打分函数**，只影响排序，不影响可行性 | 重心居中度、港序（LIFO）、空间利用率、作业步数、装卸设备适配 |
| **R 报告项** | 必须**如实记录与申报**，不参与搜索 | 输出层的合规字段 | VGM 重量、IPPC 标识、系固方案、CSC、危险品申报 |

### 2.2 关键判断：哪些"法规"其实不是算法约束

| 规范 | 它实际约束什么 | 对几何搜索的意义 |
|---|---|---|
| **IMO/ILO/UNECE CTU Code Annex 7** | 给出**重心偏移指导等级**（本项目用的 5%/10% 就出自 §3.1.4 与 Appendix 4 质量矩） | **是"指导"（guidance），不是禁令**。应当作 **S 层设计目标**：以限值 60~70% 为设计点，限值只作红线 |
| **SOLAS VI/2 VGM** | 装船前**申报验证总重** | **R 层**。约束"报告"，完全不约束几何 |
| **IMDG Code** | 危险品隔离表 | **H 层**（真硬）。但本项目无危险品场景，暂不涉及 |
| **IPPC ISPM 15** | 木质包装熏蒸/标识 | **R 层** |
| **GB 40163 / CSC** | 集装箱本体制造与标牌安全 | **R 层**，不约束装柜 |
| **船公司/码头规则** | 单柜最大净重、轴向载荷分布 | **H 层** |

**结论：真正约束几何搜索的只有碰撞、包络、堆叠承载、易碎保护、危险品隔离、轴载限重这六项。**

港序（LIFO）和重心（5%/10%）**都是偏好，不是红线**。

### 2.3 项目当前最严重的建模错误

`services/packing/EndGapCompaction.js:17-19`：

```js
const shiftX = Math.ceil(Math.max(-minX, half - container.innerLength * limitPercent / 100 - cog.x) * 1000) / 1000;
```

它把货物**平移到重心偏移精确等于 5%（或 10%）限值**。实测反算：偏移量精确等于 294.9mm（=5%×5898）、589.8mm（=10%×5898）、601.6mm（=5%×12032）。

**把设计点放在限值上 = 安全系数 1.0 = 零余量。** 任何实际偏差（地磅误差、包装吸湿、装载偏差）立刻越线。安全工程的通行做法是**取限值的 60~70% 作为设计目标**。

而这个函数自己的 `evidence.limitation` 承认：**"空白转移到门端，总容积利用率不变"**——即压实深端不带来任何收益，纯粹是把重心推到限值。

**同时它暴露了倒置：为了通过"重心验收"，牺牲了安全边际；而这一切在评分表里根本不计分。**

## 第 3 节　其他装箱软件是怎么做到装满的

### 3.1 它们用的技术范式（学术与工业界通用）

| 范式 | 说明 | 项目是否有 |
|---|---|---|
| **Extreme Point（极限点）** | 只在新货物的角点处枚举候选位，避免连续空间搜索（Crainic/Perboli/Tadei 2008） | 部分（`FloorExtremePointCandidate`，但被 `maximumInstances: 9` 限死） |
| **Maximal Spaces（最大空间）** | 用"最大空闲长方体集合"表示剩余空间，放入后更新集合（Parreño 等的 GRASP + maximal spaces） | 部分（`PlanMetrics` 里有自由空间枚举） |
| **块构建 Block/Layer Building** | **同型同尺寸货物先组成 a×b×c 的块，以块为单位摆放**（Eley 2002；Bortfeldt & Gehring） | **无** ← 最大缺口 |
| **多起点随机重启（GRASP / Iterated Greedy）** | 用随机化的构造启发式跑几百到几千次，取最优 | **无**（只有 `maximumStarts: 8`，且只在 9 实例内） |
| **Beam Search / 有限宽度树搜索** | 每层保留 K 条最优部分解 | 有，但 **K = 4** |
| **自由空间链表 + 空洞回填** | 摆放完成后把小件塞进残余空洞 | 部分（void repair，但限 30 件） |

### 3.2 为什么它们能装到 85%+

1. **块化把搜索维度从"件"降到"块"**：600 件鞋盒 → 先组成 2×4×8 的块（64 件/块），搜索对象从 600 降到约 10 个块。**组合数下降 2~3 个数量级。**
2. **默认允许任意朝向**（仅易碎/不可倒置件除外）。
3. **港序/LIFO 默认关闭**。多港口混装是可选高级功能，开启时软件会提示"利用率将下降 X%"。
4. **时间预算宽松**：秒级到分钟级，但不会出现"180 秒只装 22.8%"。
5. **未装入清单是一等输出**——这正是你说的"实在装不下的会放到旁边"。商业软件把它作为**正常业务结论**（客户据此决定加订几个柜），而不是"失败"。

### 3.3 项目缺的是什么

**不是缺算法，是缺"块构建 + 多起点重启"这两个最基本的工程手段。**

现在的做法是"逐件贪心 + 4 宽度的 beam + 14 个事后修复器"，这在组合优化里是已知会失败的结构。

## 第 4 节　如果要做，正确的算法该怎么设计

> ⚠️ 读完第 5 节再决定要不要做。CMIT 评分表里算法不直接计分。

### 五层架构

```
L0 问题建模
   货物 → 归一化包络 + 类型标签（可旋转轴集、堆叠上限、易碎、朝向限制、目标港）
   硬约束集 H（6 条，见 2.2）
   软目标集 S（重心、港序、利用率、作业步数）+ 权重

L1 空间表示
   Maximal Spaces（最大空闲长方体集合）+ Extreme Point 候选位
   ★ 只在"生成候选"时枚举 H 层可行位，不做事后过滤

L2 块构建（缺这一层是当前失败的根源）
   同 SKU + 同朝向 + 同堆叠层 → 组块（枚举 X/Y/Z 三种成组方向与层数）
   输出：块列表（尺寸 + 件数 + 重量），搜索对象从"件"变"块"

L3 搜索
   多起点随机重启（GRASP）：每次用随机化的放置序（体积降序/底面积降序/高度升/港序优先…）
   + 有限宽度 beam（K = 32~64，而不是 4）
   + 软目标打分选优（而非"第一个通过硬约束的"）
   时间预算：给足（秒级~分钟级），但必须有"随时可返回最优解"的 anytime 机制

L4 后处理
   空洞回填：用小件填残余空间（不设 30 件上限）
   重心平移：目标是限值的 60~70%，不是限值
   未装入清单：一等输出 + "需加订 N 个柜"的建议

L5 验收分级
   H 层全过 = 方案有效（这是 pass/fail）
   S 层打分 = 方案分级（A/B/C，不是通过/不通过）
   禁止把 S 层写进 pass/fail 判定
```

### 关键改动（按影响排序）

| # | 改动 | 影响 |
|---|---|---|
| 1 | **把港序与重心从 hard gate 移到 S 层打分** | 可行域从"近似空集"恢复到"正常集合"。**这是装载率崩塌的直接解药** |
| 2 | **实现块构建** | 组合数降 2~3 个数量级，大算例从"搜不动"变"搜得动" |
| 3 | **搜索宽度 4/8 → 32/64，多点随机重启** | 600 件算例的装载率应有数量级改善 |
| 4 | **H 层改"生成时剪枝"而非"生成后校验"** | 消除大量无效候选的构造与验证开销，直接解决 180s 性能问题 |
| 5 | **重心设计目标 = 限值 ×0.65**，删除 `EndGapCompaction` 的"推到限值"逻辑 | 消除零安全余量；同时它本来也不提升利用率 |
| 6 | **未装入清单作为一等输出**，并给出加订柜数建议 | 产品体验 + 商业价值（客户真正需要的东西） |
| 7 | 清理 8 套引擎中的死代码（`ShippingTimePackingEngine`、`Realistic4DPackingEngine-v33.0-FINAL` 引用数 0） | 降维护成本，避免评委看代码时困惑 |

## 第 6 节　一句话总结

> **算法的问题不是"没调好"，是范式错了**：25 个版本都在给同一个逐件贪心启发式打补丁，
> 搜索宽度始终是 4 和 8，约束从 1 层叠到 14 个修复器，可行域被压到近似空集——
> 所以 600 件小箱子装 76 m³ 的柜子，只能装进 22.8%。
>
> **但更重要的判断是：在 CMIT 这套评分表下，算法不值得再投入。**
> 赛区 100 分里，视觉效果 30 + 互动体验 30 = 60%，算法是 0。
