## 第 1 节　它对我两条批评：我核实后都接受

### 1.1 ✅ 接受：「任何业务流都起不来」过宽

它说：*"附件已经证明默认演示路径有问题，却没有证明三条正式求解路径产生的 placement 全部缺字段。"*

**我做了核实，它是对的。三条路径的真实产出：**

| 路径 | 是否产出 `orientationId` / `axisMap` | 代码位置 |
|---|---|---|
| **SOURCE** | ✅ **显式产出** | `packing/SourceBenchmarkSolver.js:32`<br>`orientation:orientation.legacyLabel, orientationId:orientation.id, canonicalOrientation:orientation.id, axisMap:{...orientation.axisMap}, uprightOriginalAxis:...` |
| **Native** | ✅ **显式产出** | `HybridConstraintPackingSolverV2.js:634-636`<br>`orientationId: dims.id \|\| dims.label, axisMap: dims.axisMap ? {...} : null` |
| **COMMERCE** | ⚠️ **未搜到**（见 1.3） | — |

而且 `packing/PlanValidator.js:57-58, 260-278` 会**读并交叉校验**这两个字段（`sameAxisMap` / `geometryMatches`）—— **说明"方向元数据必须自洽"是已有设计，不是新加要求。**

**结论：我说"任何经过正常业务流的数据都起不来"是从"`cargo.normalize` 不产出该字段"外推的，没有实测真实求解结果。这条批评成立，我撤回。**

**我实际证明的只有**：默认演示路径（`/workspace/twin` 无正式方案时走 `WORKSITE_DEMO`）起不来。**这一点双方都认。**

### 1.2 ✅ 接受：我选的修复层不对

它说：*"优先修在 preview/placement → render item 的适配边界，不在通用货物 normalize 中批量写 `orientationId=LWH`。"*

**它的架构判断是对的：**

| 对象 | 应携带 | 我错在哪 |
|---|---|---|
| **Cargo（货物定义）** | 原始尺寸、重量、数量、**允许方向集合** | 我在这里写死 `LWH` —— 但一只 SKU 有 50 件时，求解后完全可能有的 `LWH` 有的 `WLH` |
| **Preview item** | 为展示选择的**预览姿态**（注明非求解结果） | 我没区分这一层 |
| **Placement** | 每个**物理件实际**采用的位置与方向 | 我没区分这一层 |

**一个补充精确化**：对 `FIXED_ORIENTATION` 的货物，允许集合是单元素 `{LWH}`，所以**在 cargo 层写 `LWH` 语义上不算错**。但**对方选的层更对**——因为修在 preview/placement 适配边界可以**同时覆盖**"历史数据缺字段"与"预览姿态"两种情形，且**不改变 cargo 的语义**。**我采纳它的分层。**

它给的三分处理我也完全认同：
1. 默认演示预览 → 预览生成器按明确允许方向造展示姿态，标 `PREVIEW`，不写回求解选择
2. 新生成的正式方案 → **由求解输出适配器逐件提供**，不让前端事后补
3. 历史方案缺字段 → **仅在能唯一证明时重建**；有歧义或冲突就报错

并且它强调 *"不删除严格反例断言，不增加全局'缺字段就 LWH'兜底"* —— **正确**，`placementAxisMap({})` 抛错这条测试必须保留。

### 1.3 我的增量：COMMERCE 路径疑似不产出（双方都没提）

我在 `CommercePackingService.js` / `packing/CommerceWallPacker.js` / `packing/CommerceColumnPacker.js` 里**没有搜到 `orientationId` 或 `axisMap`**。

**如果成立**，则 COMMERCE 路径的结果送进 `PrecisionCargoFactory` 会走同一条抛错逻辑。**这是一个需要实测确认的新疑点**，不预设结论（可能字段在更下游的适配器里补）。

建议在三条路径冒烟时**专门记录**：每路返回的 placement 是否带 `orientationId` / `axisMap`。

## 第 2 节　它的最大贡献：战略转向成熟内核 —— 我已核实成立

### 2.1 核实结果：Windows 预编译包真实存在

我抓取了官方 Releases 页（`github.com/fontanf/packingsolver/releases`），当前 `latest` 资产：

| 资产 | 大小 | SHA-256 | 构建时间 |
|---|---|---|---|
| `packingsolver-linux-x64.tar.gz` | 27.7 MB | `c5fdf4e5…` | 2026-09-18T08:34:15Z |
| `packingsolver-macos-x64.tar.gz` | 21.6 MB | `ee8d8e21…` | 2026-09-18T08:34:15Z |
| **`packingsolver-windows-x64.zip`** | **16.8 MB** | **`b142bfbc…`** | **2026-09-18T08:34:15Z** |

**方案说的"官方已提供 Windows x64 预编译包"成立。** 而且是今天早上刚构建的。

其他已核实的事实：
- `latest` 是 **CI 从 master 自动构建**，当前对应 commit `9bfb943`，页面明确写 **"not versioned releases"**
- 版本化 release：**v1.1.0（2026-09-09）**、v1.0.0（2026-07-09）、0.8、0.7…
- **v1.0.0 新增 `boxstacks` / `rectangle` / `onedimensional`** —— 与方案说的一致
- 0.3 版本说明：**"PackingSolver now compiles and runs on Windows"**

**→ 方案关于 problem type 的区分（`box` 一般三维箱件 / `boxstacks` 同底面柱结构 / `irregular` 是二维）也与官方发布说明一致。**

### 2.2 但它漏了一个版本冻结张力（我补）

**方案说**：*"latest 会变化：下载后固定当前二进制、源码版本和 SHA-256，不在每次启动时自动更新。"*

**问题在于**：
- **预编译二进制只有 `latest`** —— 它每次 master 提交都重建
- **版本化 release（v1.1.0 / v1.0.0）只有源码（Assets 2），没有二进制**

→ 所以"固定版本"这条**只能做到一半**：你可以固定**你下载的那个二进制的哈希**，但它对应的是**当天 master 的某个 commit**，不是一个 release。**要真正冻结到一个版本化 release，就必须自己编译** —— 而这与方案"优先用预编译包、不搭编译环境"的取向矛盾。

**实务建议（我补的三条）**：
1. 下载时**同时归档**三样：二进制 + SHA-256 + **对应 commit `9bfb943`**
2. 在 adapter 里**硬编码期望哈希**，启动时校验；不匹配就拒绝执行（防止有人换了二进制）
3. 在报告里写清**我们测的是 master@9bfb943 的 CI 构建，不是 v1.1.0** —— 答辩时被问到版本要答得出来

### 2.3 接口陷阱清单质量很高，我全部认同

它的三条陷阱我都认，尤其两条：

- **"朝向空集合不能传六个 0"** —— 文档说未设置旋转列时取默认方向，传六个 0 会从"没有合法方向"变成"默认方向可以"。**这是真实的语义反转风险。**
- **"Y/Z 竖直轴差异"** —— 项目是 X 长 / **Y 竖直** / Z 横向；PackingSolver 文档默认 **Z 竖直**。必须显式双向映射，并用**三边不同的箱子测六种方向**。

第三条（"几何更好 ≠ 业务通过"）也对：box 内核给出高利用率，**不代表它执行了 WTPACK 的 kg/cm² 接触压力模型**；而"靠最后 validator 不断拒绝"不会让搜索学会这些条件。

### 2.4 两个工作日预算

**合理。** 战略转向的潜在收益（停止无限自研循环）远大于两天成本。而且它设了明确的决策出口（`PROMOTE_FOR_DECLARED_SCOPE` / `KEEP_AS_GEOMETRY_CANDIDATE` / `REJECT_OR_BLOCKED`），**不是"再调研一轮"**。
