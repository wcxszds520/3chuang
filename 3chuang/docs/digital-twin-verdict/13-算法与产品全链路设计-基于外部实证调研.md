## 第 0 节　先纠正一个前提：算法不该"按法规"设计

用户的原始问题是"算法到底按什么约定约束——按国家/行业/货代/港口法规，还是怎么样"。

**调研给出的答案很明确：都不是。正确做法是"约束分层 + 按本次任务过滤"。**

商业软件的实际做法（EasyCargo 官网）：

> "Restriction settings - **rotation, stackability, and tiltability**"
> "**Priority groups** categorizing cargo items based on the final destination"
> "The possibility to **split items by a virtual wall**"

**它们不写"法规引擎"，而是把约束做成三类东西：**
1. **每件货的约束属性**（能否旋转 / 可否堆叠 / 可否倾斜 / 朝向限制）
2. **分组**（按目的地、批次、客户）
3. **全局限制**（柜内尺寸、限重、轴载）

**法规只在极少数地方成为"硬边界"**（VGM 重量、危险品隔离、总重），而这些边界商业软件也是做成"检查项与申报项"，不是做成"几何搜索的约束"。

**所以正确的回答是**：法规是**约束源之一**，不是算法设计的出发点。算法应按**约束的性质（候选剪枝 / 终态校验 / 优化目标 / 申报项）**分层，再按**本次任务**决定哪些生效。

## 第 1 节　外部软件的真实算法设计（有据可查）

### 1.1 学术谱系：40 年，五条主线

| 年代 | 方法 | 代表 |
|---|---|---|
| 1980 | **墙式构建 Wall-building** | George & Robinson —— 第一个较成熟的 CLP 启发式 |
| 1997–2002 | **柱式构建 Column-building** + 遗传算法 | Gehring & Bortfeldt；后续 Tabu Search、混合遗传、并行版 |
| — | **块构建 Block + 树搜索** | Eley —— 贪心生成块，再用树搜索组合 |
| — | **GRASP + 修改版墙式** | Moura & Oliveira |
| 2003– | **最大空间 Maximal-Space + GRASP** | Parreño, Alvarez-Valdes, Oliveira, Tamarit —— **在 Bischoff & Ratcliff 全部 15 类 1500 题上超越所有非并行方法** |
| — | **极端点 Extreme Point** | Crainic, Perboli, Tadei |
| 2006– | **承重约束**（有限承载强度） | Bischoff —— 把堆叠承压纳入模型 |
| 2013 | **约束综述**（该领域权威分类） | Bortfeldt & Wäscher, *Constraints in container loading — A state-of-the-art review* |
| **2026** | **两阶段混合装载算法 THLA**（选柜 + 装载，同时考虑 multi-drop / 几何 / 承压） | Jia et al., *Computers & Industrial Engineering* 213:111779 |

**关键结论：没有任何商业或学术实现"求解最优"。全部是「构造启发式 + 多策略 + 随机重启 + 局部改进」。**

### 1.2 商业软件的功能清单（读出来的设计意图）

**EasyCargo**（捷克，$799/年）：
- **10 000+ 件/单**（规模上限远高于我们）
- **Priority groups**（按目的地分组）
- **Restriction settings**：rotation / stackability / **tiltability**
- **Virtual wall split**（虚拟墙分割货物）
- Step-by-step **multi-cargo-space** plan（多柜分步计划）
- **Weight distribution verification with permitted limits**（重量分布按许可限值校验）
- 手动拖拽编辑器 + auto-snap
- Excel / API / SAP 集成
- **估算柜数时建议留 10% 余量**（承认"完全利用不可能"）

**CargoWiz**（SoftTruck）：
- **Mixed Cargo Sizes**："expecting cargo to have **any variety of cargo dimensions**"
- **Mixed Container Sizes**：**装完 40 尺剩货，直接切 20 尺**（"Reduces shipping costs and damages"）
- **Stage Area**：模拟月台，**图形化显示装了什么、还剩什么**（对应我们的"未装入清单"）
- **Load Steps Review**：一步步看装载顺序
- 必填/选填分色（粉=必填，蓝=选填），**其余自动生成**
- 多语言（含中文）

**MaxLoad Pro**（TOPS）：
- **Loads cylindrical, L-shaped, trapezoidal and bundled SKUs**（明确支持异形）
- **cylindrical SKUs in nested or pyramidal patterns**（圆柱可**嵌套/金字塔排列**，不只是外接框）
- Mixed pallets；drop offs（多站点）；axle weights（轴载）
- **"Compare solutions to find the best mix of vehicles to optimize cube usage and minimize costs"** —— **比的是"柜型组合 + 成本"，不是单柜利用率**
- Server Mode 黑盒模式

**3DPACK.ING**：
- **一次优化中定义多种柜型，算法评估所有组合**，统一考虑空间利用率、重量分布、**成本**

### 1.3 异形货物怎么处理 —— 行业有标准答案

**答案：最小外接长方体（Minimum Bounding Box）+ 朝向规则。**

| 形态 | 处理 |
|---|---|
| 圆柱（桶/管/卷） | **直径 = 宽 = 高**，长度 = 长。**不用 πr²h** |
| 球 | 直径用于三个维度 |
| L 形 | 拆两个长方体 **或** 整体外接框（让用户选） |
| 锥 / 金字塔 | 最宽底 + 最高点 |

**为什么按外接框算**（原文）：

> "If you have a cylinder, you cannot easily stack other boxes on top of it without them falling off. **The 'lost space' around the cylinder is unusable for other cargo**"

**例外**：MaxLoad Pro 支持圆柱的 **nested / pyramidal** 排列（即真正利用圆柱间的空隙），但这是**高级特性**，不是基准做法。

### 1.4 多批次 / 多目的地 / 多 SKU 怎么处理 —— 核心是「分组」，不是「把顺序塞进搜索」

**学术侧**（Jia et al. 2026 摘要原文）：

> "orders required by the **nearest customer should be loaded later** so that these items can be **unloaded earlier, and fewer items are removed**... Furthermore, **reloading efforts should be avoided**"

**实务侧**（Hansatic 多柜规划指南）：
- **40%+ 的货运使用 2 个以上柜**；人工分批平均**浪费 18% 空间**
- 6 步：算总重体积 → **选柜型** → **按目的港分组合规分配** → **跨柜重量平衡** → 每柜独立装载顺序（多站点用 LIFO）→ 每柜独立单据
- **常见错误清单**（这张表价值很高）：
  - 独立优化各柜（A 柜 98%、B 柜 55%）
  - **拆散配套货物**（同一订单的部件分到不同柜）
  - 忽略单柜限重（总体没超，单柜超了）
  - 无跨柜协调
  - 手工改动后要重算全部分批
  - **订舱早于规划**（先订了两个 40 尺，才发现一个 40 尺 + 一个 20 尺更便宜）

**关键设计启示**：
> **"多批次 / 多目的地"应当作为「分组键」在搜索之前处理，而不是作为「约束」塞进几何搜索。**

这正是我们项目犯的错——把港序当硬约束塞进求解器，导致可行域收缩。

### 1.5 多柜 / 选柜的权威框架

**MCLP（多柜装载问题）= 两个子问题**（Meliani et al. 2022；Jia et al. 2026）：

```
子问题 1：Container Selection（选柜）—— 选哪些柜型、各几个
子问题 2：Item Loading（装柜）—— 每柜怎么装
```

**目标分两类**（Bortfeldt & Wäscher 2013；Zhao et al. 2016）：

| 类型 | 目标 | 适用 |
|---|---|---|
| **Input minimization** | **最小化柜数 / 柜总体积 / 成本**（要求全部装完） | 货代场景 —— **我们的场景** |
| **Output maximization** | 最大化装入体积/价值（不要求全装） | 单柜、货量不足场景 |

**2026 最新解法（THLA）**：
- 选柜用 **greedy selection + refined search** 两种策略
- 装柜用 **模拟退火 + 启发式**
- 提出 **space recycling 策略**减少空间浪费
- 同时考虑 **multi-drop + geometric + load-bearing** 三类约束

**选柜的实务启发规则**（Hansatic）：
> **重货密集货 → 20'（限重风险低）；轻抛货 → 40'HC**

## 第 2 节　算法内核的正确设计（五层）

```
┌─ L0 输入规范化 ────────────────────────────────────────┐
│  形态归一：异形 → 最小外接框（圆柱=直径x直径x长）        │
│  分组键：目的地 / 批次 / 客户 / 不可拆配套组             │
│  本次适用约束：从规则库按 applicability 过滤             │
│  缺失处理：缺重量 → 可做几何研究，不得生成重量安全结论   │
└──────────────────────────────────────────────────────┘
                        ↓
┌─ L1 分组与分批（处理多 SKU / 多批次 / 多目的地的核心）──┐
│  先分组 → 组内装箱 → 组间关系用「装载顺序」表达         │
│  ★ 不把顺序塞进几何搜索（这是我们当前的错误）           │
│  不可拆配套组作为原子单位，不得跨柜拆分                 │
└──────────────────────────────────────────────────────┘
                        ↓
┌─ L2 块 / 墙 / 柱构建 ─────────────────────────────────┐
│  同 SKU 同朝向组块（nx × ny × nz）                     │
│  ★ 保留尺寸梯度 + 单件回退（不能只留大块）              │
│  圆柱组可尝试 nested / pyramidal（高级）                │
└──────────────────────────────────────────────────────┘
                        ↓
┌─ L3 空间表示与搜索 ───────────────────────────────────┐
│  Maximal Spaces（六向切分 + 支配剪枝） + Extreme Points │
│  多策略组合：volume / footprint / wall / layer / strength│
│  多起点随机重启（GRASP）                                │
│  ★ 全程共享一个 deadline，保留 anytime 最优 incumbent   │
└──────────────────────────────────────────────────────┘
                        ↓
┌─ L4 后处理 ───────────────────────────────────────────┐
│  空洞回填（用小件填残余）                               │
│  刚性平移居中：目标 = 0，不是推到限值（已纠正）          │
│  未装入清单一等输出 + 加订柜建议                        │
└──────────────────────────────────────────────────────┘
                        ↓
┌─ L5 分层校验 ─────────────────────────────────────────┐
│  CANDIDATE  候选生成时剪枝（碰撞 / 包络 / 朝向 / 层数） │
│  TERMINAL   终态全量校验（承压 / 重心 / 作业可行性）     │
│  DECLARATION 出运准备（VGM / 单证 / 系固）——不进搜索    │
└──────────────────────────────────────────────────────┘
```

**多柜层（L6，与单柜解耦）**：
```
选柜（Container Selection）
   ├ 目标：input minimization（最小化柜数与成本）
   ├ 策略：greedy selection + refined search（THLA）
   └ 启发：重货密集 → 20'；轻抛 → 40'HC
        ↓
分配（Cargo Allocation）
   ├ 先按目的地 / 批次分组
   ├ 不可拆配套组作为原子单位
   └ 跨柜重量平衡（每柜独立满足限重）
        ↓
逐柜调用单柜算法（L0–L5）
```

## 第 3 节　按你说的六个模块的改造设计

### 3.1 货物录入

**现状问题**：字段是扁平表格（length / width / height / weight / stackable / ...），**无法表达异形、成套件、批次归属**。

**改造**：

| 新增 | 设计 |
|---|---|
| **形态层** | 标准长方体 / 圆柱 / 卷 / L形 / 托盘 / **成套件（kit）** |
| 圆柱输入 | 只输入**直径 + 长度**，系统自动转外接框（宽=高=直径），并标记"是否可嵌套排列" |
| L形输入 | 提供两个选项：拆两件 / 整体外接框（让用户决定） |
| 成套件 | **绑定为不可拆分组**（避免 Hansatic 说的"拆散配套"错误） |
| **批次字段** | 目的地 / 到货批次 / 客户 / 订单号（作为**分组键**，不是约束） |

**必填 / 选填分层**（CargoWiz 做法：粉=必填、蓝=选填、其余自动生成）：
- 必填：尺寸、数量
- 选填：重量 —— **缺失时明确标注"不得生成重量安全结论"**
- 自动派生：体积、密度、是否重货（**按密度，不是按 20 kg**）

### 3.2 柜型选择

**现状问题**：分别对每个柜型求解取最好，不是组合优化。

**改造**（按 MCLP 权威框架）：
1. **明确目标类型**：我们的场景是 **input minimization**（最小化柜数与成本），不是最大化利用率
2. **混合柜型组合优化**：在一次优化中评估"20' × a + 40' × b + 40'HC × c"的组合，而不是逐个柜型各解一次
3. **启发规则**：重货密集 → 20'；轻抛 → 40'HC
4. **输出成本而非只输出利用率**（MaxLoad Pro 的 "compare solutions ... minimize costs"）

### 3.3 法规匹配

**现状问题**：所有约束压成一层 pass/fail 门禁（已确认），可行域被压到近似空集。

**改造**：规则对象采用七个字段（这一设计来自对方案的严格要求，我采纳）：

```
source / sourceVersion / clause   从哪里来
applicability                      适用于哪个任务
enforcement                        候选条件 / 终态条件 / 优化目标 / 出运检查
parameters / units                 数值与单位（VGM 的 5% 与重心的 5% 必须分开）
missingDataPolicy                  阻断 / 未执行 / 不适用
implementationStatus               已执行 / 部分支持 / 不支持
```

**核心原则**：**法定性质与算法 enforcement 分开**。一条规则是否法律强制，与它在求解器里是否硬约束，**是两件事**。

**不建"全球法规平台"**，只覆盖本次任务真正适用的。

### 3.4 3D 数字孪生演示

**已定位的三处修复**（前几轮实测）：
- 雾：`Fog(18,48)` + `maxDistance 38` → 拉远即糊，改 2 个数字
- 主体材质 anisotropy 丢失（`pc_cardboard.001` / `pc_wood` = 1，同场景其他 = 8）
- `finishInspectionMaterial` 硬覆盖 GLB 的 roughness/metalness

**新增两项高价值可视化**（都有实务依据）：
- **重量分布带**：按箱长分段显示各段重量占比（**可视化，不是规则**。参照 CTU Code "rule of thumb" 的图示习惯，但不做硬判定）
- **门端间隙 + 系固提示**：显示门端空隙（实务检查员会量这个），超过阈值给出**系固建议**而非自动判定不合格
- **未装入清单 + Stage 区**（对应 CargoWiz 的 Stage Area）：一等他输出，配合"加订 N 个柜"建议

### 3.5 Landing 页

**现状**：hero 已经是产品级（实测），但定位叙事不清。

**改造**：
- 一句话讲清**卖给谁、解决什么**（当前报告已有用户调研，但界面没体现）
- 展示**算法能力边界**：能处理什么（多 SKU / 异形 / 多批次 / 多柜选型），**不吹"装满"**
- 补一个**"看它能做什么"的交互演示**（对应「互动体验 30 分」）

## 第 6 节　一句话总结

> **算法不该"按法规"设计。** 商业软件的做法是：把约束拆成「每件货的属性」「分组」「全局限制」三类，让用户配置本次适用；法规只在极少数地方成为硬边界，而多数成为**申报项**。
>
> **外部软件的核心手段不是"更聪明的搜索"，而是三件事**：
> ① **分组**（目的地/批次/客户）——把多批次多目的地问题在搜索之前解决
> ② **形态归一**（异形 → 外接框 + 朝向规则）——把几何复杂度在输入之前解决
> ③ **选柜与装载分离**（MCLP 两阶段）——把多柜问题在单柜问题之外解决
>
> **我们当前把这三件都做成了"塞进搜索的约束"，所以可行域被压死。** 这是设计错误，不是参数问题。
