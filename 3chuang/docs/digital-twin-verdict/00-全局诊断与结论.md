## 一、三个问题的直接回答

| 你的疑问 | 结论 | 一句话理由 |
|---|---|---|
| 是 Three.js 的上限不够吗？ | **不是** | three.js r185 已支持 Nanite 式 compute 光栅化、WebGPU skinning+instancing。你卡的不是引擎能力，是资产预算。 |
| 是 MCP 的能力不够吗？ | **不是，但 MCP 被误用了** | MCP 官方几何工具只有 `add_primitive`（cube/sphere/cylinder/cone/plane/torus）+ `execute_blender_code`。它天生只能"堆图元"，不负责拓扑与面数。 |
| 要不要换技术 / 换代码 / 换建模？ | **换建模产线 + 换渲染策略；技术栈与代码架构都不换** | 你的 React + three 分层、领域模型、RAG 溯源、状态机、测试覆盖都已经是加分项，推倒重来是净损失。 |

### 但也要说清楚：draw call 不是画面难看的首因

修正 draw call 数字之后，必须同步修正一个结论：**画面"扁平玩具感"的主因不是预算，而是光照与材质策略**（详见 `agent-02-视觉特效总监` 的诊断）。`RoomEnvironment` 室内影棚贴图 + `environmentIntensity 0.48` + `HemisphereLight 0.32` 三者叠加，才是"像在摄影棚里拍积木"的直接原因，且**修它只需改 5 个数字，不需要动一个资产**。

真正的资产侧硬伤有两个，且都是**加载与显存**问题而非帧率问题：
1. 集装箱 GLB **8 MB**，首屏必加载，光图片就 1.4 MB（未压缩 PNG）
2. 集装箱 **147,018 三角面** + 叉车 **113,996 三角面**——批处理能降 draw call，但**降不了三角面**（阴影 pass 还会翻倍）

调用链里还有两处**直接按件加载 GLB** 的路径需要注意：`TaskOverviewScene.jsx:66` 与 `PackagingModelViewer.jsx:53` 都走 `loadPackagingAsset()`，那里才是 107 网格纸箱真正被逐件渲染的地方。

## 三、根因拆解（四层归因）

### L1 建模层：MCP 只能"堆图元"，必然网格爆炸

Blender MCP 暴露的几何能力就是 `add_primitive`（7 种基础图元）+ `execute_blender_code`。这意味着 LLM 驱动的建模本质上只能做**图元装配**。你的资产结构完美印证了这一点：

- 一个纸箱 = 107 个独立网格（因为要"3mm 折翼、胶带重叠、瓦楞芯"各建一个）
- 一台叉车 = 453 个独立网格（链条板、销轴、链轮、油缸、后视镜…各建一个）

`assets-src/blender/rebuild_v3/asset-contract.json` 里白纸黑字写着这批资产的设计目标是：
> "Separate three-millimetre folding flaps, paper grain, tape overlaps, card flutes, generic label/barcode and restrained corner creases"

**这是"细节最大化"方向——对离线渲染是对的，对实时 Web 是反向的。** 结果：纸箱从 32 KB 涨到 2,027 KB（65 倍），同时网格数从 1 涨到 107。

MCP 还有几个硬边界要知道（都已在官方文档确认）：
- **没有实时视口流**，模型只能看单张截图 → 它无法感知比例失调、穿插、重心漂移
- **导出会超时**，必须走 headless CLI —— 你的 `build_*.py` 走 CLI 是对的
- **程序化贴图不会导出 glTF**（Noise→Roughness、ColorRamp、Bump 全部丢失），必须烘焙
- **节点名会被改写**（空格→下划线、点号删除）→ 运行时按名字找关节会失配

**结论：MCP 是"打字员"，不是"建模师"。它忠实执行你的意图，但不会替你判断拓扑合理性、面数预算和 LOD 划分。**

### L2 资产层：没有预算合同，也没有压缩闸门

现有管线缺四样东西，每一样都是数量级差距：

| 缺失环节 | 现状 | 应有状态 | 收益 |
|---|---|---|---|
| 网格合并 | 纸箱 107 网格 / 叉车 453 网格 | 静态件合并为 1–3 个网格 | draw call 降 50–100 倍 |
| 实例化 | 每件货物独立渲染 | 同型货物走 `InstancedMesh` | draw call 降 40 倍 |
| 贴图压缩 | 内嵌 PNG，单张 254–374 KB | KTX2 / BasisU，≤1024px | 显存降 4–8 倍 |
| 几何压缩 | 未压缩 GLB，8 MB | gltfpack `-cc`（meshopt） | 体积降 80–90% |

顺带一提：项目里**已经有 `addInstancedBoxes()` 并且写了 `InstancedMesh` 逻辑**（`scene/sharedResources.js:32-53`），但 rebuild-v3 的重资产直接绕过了这条路径。

### L3 渲染层：策略选错了，而不是参数没调好

逐一核对 `three/TwinScene.jsx`：

| 位置 | 现状 | 问题 |
|---|---|---|
| `:266` | `scene.environmentIntensity = 0.48` | 环境光被压到一半，金属没反射、暗部死黑 |
| `:290`, `:842` | `RoomEnvironment` → PMREM | **用的是室内影棚环境**，不是港口天空。这是"看起来像在摄影棚拍积木"的主因 |
| `:303` | `HemisphereLight(..., 0.32)` | 环境光强度极低，对比僵硬 |
| `:269–283` | 阴影 `autoUpdate = false` | **这不是"优化"，是"掩盖"**：`invalidateShadows()` 只在离散事件触发，而 `updateRuntime` 每帧驱动叉车/工人运动——平滑运动时阴影图不刷新，关节与货叉投影会滞后抖动 |
| `:292`, `:872–903` | GTAO(16 samples) + SMAA + OutputPass，`pixelRatio` 最高 2 | 后处理成本与场景复杂度无关、全是全屏 pass；`pixelRatio 2` 在 4K 屏等于渲染 4 倍像素，且会**同时放大 GTAO 与 SMAA**，是乘法成本 |
| `:356/359/361` | `createIndustrialContainer` / `createIndustrialForklift` / `createManualWorker` | 这三个是**程序化 fallback**；`:465 hydrateHeroAssets` 会在 GLB 加载完成后把它们 `visible = false` 切掉（见 `:484 / :503 / :540`）。所以是**两套并行资产线**：程序化兜底 + GLB 正片，风格与材质需要两边同步维护 |

**注意最后一条**：真正的渲染走 GLB，但程序化兜底代码全部保留并在同一场景里存活。这意味着每次改外观要改两处，且两条线的外观语言并不一致——这是"效果始终不尽人意"的一个被低估的原因。

**还有一处结构性问题**：`batchStaticAsset()`（`:637`）是一个写得很完整的静态网格合并函数，但**只有叉车调用了它**（`:510`）。集装箱（`:475`）、工人（`:518 / :533`）、地牛（`:467`）三处都没有调用——这是 478 个 draw call 的直接来源。

### L4 设计层：视觉语言是"CAD 示意图"，不是"物理现场"

看 `output/playwright/commercial-05-after-standard.png`（9/8，目前最好的一版）：集装箱波纹墙、锁杆、印刷标签纸箱都做出来了，已经能打。但对比 `docs/design_reviews/round2-stage-4-twin-3d.png` 的线框容器，问题很清楚：

- **半透明箱壁 + 网格线** 被当成默认视图 → `BLACKBOX` 里也承认"半透明箱壁及网格仍减弱货物辨识"
- 剖切/线框应该是**一个模式**（"看清内部"），而不是**默认状态**
- 数字孪生的默认视图应该是"物理现场感"，因为孪生的说服力来自"这看起来是真的"

## 四、Three.js 的上限到底在哪里

**上限不在引擎，在预算。** 但你的版本确实落后了：

| 能力 | 你的版本（r179） | 最新（r184/r185，2026-04 / 2026-07） |
|---|---|---|
| WebGPU 渲染器 | 可实验 | r171 起生产可用，Safari 26 已支持 → 约 95% 覆盖 |
| 后处理 | `EffectComposer` + Pass 链 | r183 改名 `RenderPipeline`（节点式），旧代码会静默失效 |
| 着色器 | GLSL 为主 | **TSL 已成默认**，一次编写编译到 WGSL/GLSL 双端 |
| 万级物体 | 需手工优化 | r160 起 `InstancedMesh` 自动合批，draw call 降约 60% |
| 超高模 | 不可能 | **r185 引入 Nanite 式 compute 光栅化**（百万三角面可跑） |
| 骨骼 | CPU 侧瓶颈 | r185 WebGPU skinning + instancing，可实例化蒙皮网格 |
| 模型加载 | — | r160 重写 Draco v3，加载时间降约 40% |

**但要给一个明确的否定结论：升级 three 解决不了你的 draw call 问题。** r160 的自动合批与 r185 的 compute 光栅化都是"兜底峰值"的手段，替代不了正确的资产预算与静态合并——580 → 120 这一降，靠的是 `batchStaticAsset()`，和引擎版本无关。r185 的价值在于你在**预算修好之后**能把 pixelRatio、GTAO、LOD 再加回去。

## 五、MCP 能力边界（一句话版）

> Blender MCP 提供的是：7 种基础图元的增删、纯色材质、截图、以及任意 Python。
> 它不提供：实时视口、拓扑质量判断、面数预算、UV 规划、LOD 划分、烘焙决策。

**因此正确的用法是把 Blender 从"生成器"降级为"烘焙器"**：几何可以在 Blender 里产，但必须过一道 `decimate → UV pack → bake(normal/AO) → gltfpack` 的自动闸门。

## 六、Tripo 该不该用

Tripo P2.0（2026-09-01 发布）这次升级很关键：
- 首次实现**扩散模型端到端原生四边面拓扑**，不用事后重拓扑
- 单模型最高 25,000 quad / 50,000 tri，**可按面数预算控制**
- 语义级自动分件、人形自动绑骨、T-pose 输出
- Blender / Unity / Unreal / Godot / Cocos 官方插件
- 有 `Retopology`（百万面→几千面）、PBR 五图自动生成（Albedo/Normal/Roughness/Metallic/AO）

### 分配建议

| 资产类别 | 用什么 | 理由 |
|---|---|---|
| 集装箱 20GP/40GP/40HQ | **参数化程序生成**（保留现状） | 尺寸是国际标准，必须与求解器几何严格一致，AI 不能脑补 |
| 纸箱 / 托盘货 / 木箱 | **参数化 + 合并 + 实例化** | 要实例化几十上百次；尺寸来自算法装填结果 |
| 叉车 / 工人 / 地牛 | **可换 Tripo 出基底 + Blender 精修** | 形状自由、数量少、要"上镜"；但**必须保留命名枢轴**（升降/转向/骨骼） |
| IBC 桶 / 油桶 / 设备箱 | **Tripo 优先** | 曲面零件，程序化建模性价比低 |
| 地坪 / 龙门吊 / 堆场环境 | **Tripo 或 HDRI + 程序化** | 一次性 hero 场景 |

⚠️ 两个必须知道的坑：
1. AI 生成模型**仍需人工修破面与非流形边**（行业共识：AI 出初稿 → Blender 修 → 重拓扑 → 调材质）。
2. **面数可控是新增能力，务必设上限导出**，否则默认输出会再给你一个 10 万面的叉车。

**底线：Tripo 覆盖 hero/装饰件约 20% 的资产；80% 的参数化件必须走"程序化生成 + 烘焙 + 压缩"。**

## 七、数字孪生到底该怎么做

数字孪生 ≠ 一个好看的 3D 模型。它由四层组成：

| 层 | 内容 | 你的现状 |
|---|---|---|
| **几何孪生** | 有预算上限的、可信的物理外观 | ⚠️ **拖后腿的一层** |
| **数据孪生** | 每个 mesh ↔ 真实实体 ID ↔ 事实卡（尺寸/重量/港序） | ✅ 做得好，有事实绑定与守卫 |
| **状态孪生** | 状态机 + 时间轴回放 + 装卸推演 | ✅ 做得好，双向 42 件状态机 |
| **语义孪生** | 为什么在这、依据哪条法规、谁负责 | ✅ 做得很好，RAG 溯源 + Source Reader |

**这是一个非常重要的结论：你的第 2/3/4 层已经超过绝大多数课程作业的水平。你只需要补第 1 层，不需要推倒重来。**

这也是为什么"换技术栈"是错误的答案——你会把已经做好的三层一起丢掉。

## 八、修复路线（按投入产出排序）

### P0 —— 1~2 天，不换技术栈，立刻见效

1. **改 5 个数字救光照**（零成本、当天见效，是**最高 ROI** 的一项）：
   - `environmentIntensity` 0.48 → **1.0**
   - `HemisphereLight` 0.32 → **1.15**，地面色 `#252321` → `#3d3a34`
   - `toneMappingExposure` 1.04 → **0.96**
   - `Fog(18, 48)` → **`Fog(34, 90)`**
   - 轮廓光 `rim` 2.1 → **1.4**（2.1 会在箱体边缘烧出发白描边，是"棚拍打边"的元凶）
2. **给集装箱 / 工人 / 地牛补调 `batchStaticAsset()`**（`:637`，你已写好且叉车在用）：
   - 集装箱 `:475` onReady 后加 `batchStaticAsset(scene, 'container-static', [doors.leftPivot, doors.rightPivot])` → 210 → ~17
   - 工人 `:533` onReady 后加（保留 `rig` 枢轴节点）→ 84 ×2 → ~14
   - 地牛 `:467` onReady 后加 → 50 ×2 → ~10
   - **合计 478 → 约 40 draw call**，全场景 580 → ~120
3. **容器默认实体化**：近壁 `opacity 0.27 → 1.0`、顶板 `0.15 → 1.0`，线框/剖切降级为"模式开关"（`applyHeroContainerMode` 已有 review 分支可复用）。
4. **加资产压缩闸门**：`gltfpack -cc -tc -kn -km`。`-kn` 保留命名节点（关节靠节点名驱动，**漏了货叉就不动**）、`-km` 保留材质名（`calibrateRuntimeAssetMaterials` 靠正则匹配材质名）。预期 8 MB → 2.4 MB。
5. **`pixelRatio` 2 → 1.5，GTAO `resolutionScale` 1 → 0.75**（4K 屏省 44% 像素成本），守住 SMAA。

> 注意：第 2 条替换了初版建议中的"同型货物改 InstancedMesh"——**那条已经做过了**（`:1591 initializePlacedBatches`），不需要重复投入。

### P1 —— 3~7 天

6. **建立资产预算合同并挂 CI**（用 `tools/glb-inspect.js` 做闸门）：
   - 三角面：货物 ≤ 1,500 / 容器 ≤ 5,000 / 角色 ≤ 8,000

## 九、换什么 / 不换什么（决策表）

| 项目 | 决策 | 理由 |
|---|---|---|
| 换技术栈？ | **不换** | three.js 是 Web 3D 的事实标准；r185 已有 Nanite 式光栅化 |
| 换引擎（UE5 等）？ | **不换** | 你要 Web 端交付；除非目标是影视级渲染，否则代价与收益不成比例 |
| 换代码架构？ | **不换** | React + three 分层、领域模型、测试覆盖、事实守卫都是资产 |
| 换建模方式？ | **换** | Blender MCP 脚本堆图元 → 参数化生成 + Tripo hero 件 + 强制烘焙 |
| 换渲染策略？ | **换** | 补批处理（478 个可省 draw call）+ LOD + 压缩 + **正确的环境光照** |
| 上 Tripo？ | **部分上** | 仅覆盖 hero / 装饰件约 20% |
| 上 WebGPU？ | **计划上** | r185 + WebGL2 自动兜底，约 95% 覆盖 |
| 上数字孪生四层？ | **补第一层** | 2/3/4 层已达标，不要重做 |
| 重建程序化资产？ | **不重建** | 它们已被 GLB 取代（`visible=false`），只当兜底保留 |

## 十、一句话总结

> 你不是被 Three.js 的天花板卡住了，也不是被 MCP 卡住了。
> 画面的"玩具感"，**七成是光照选错了环境贴图**（室内影棚照户外港口），改 5 个数字就能救回来；
> 剩下的问题是**你把 `batchStaticAsset()` 写好了却只在叉车上调用了一次**——集装箱、工人、地牛三处漏调，白送 478 个 draw call。
>
> 所以优先级是：**先改光照（0 成本）→ 再补批处理（改代码）→ 然后才是压缩与资产瘦身（改资产）→ 最后才是升级引擎。**
> Tripo 用在那 20% 真正需要"好看"的地方；集装箱和纸箱必须参数化，因为它们要和求解器几何严丝合缝。
>
> 一句话：**你缺的不是钱（换技术栈），是收尾。**
