# 补漏：算法缺陷与视觉缺陷深挖（2026-09-18 第二轮实测）

> 触发：用户指出我第一轮**只查了渲染管线，没查算法**，且看图**只看了一个机位**，没有验证"远看糊、货物粘在一起、没有高级感"。
> 结论：**用户判断正确。** 本轮补出 8 项算法缺陷 + 4 项视觉缺陷，均有代码或实测证据。

## 第一部分　算法缺陷（货代总工程师视角）

### A1【最严重】重心超标永远不阻断，只给"警告"

`backend/services/compliance/DeterministicComplianceEngine.js` 的 `_cogRow`：

```js
const pass = Math.abs(lateralOffset) <= policy.cog.lateralWarningPercent      // 5
  && Math.abs(longitudinalOffset) <= policy.cog.longitudinalWarningPercent;   // 10
return row('cog', '物理重心与装载', `横向≤5% 纵向≤10%`, `横X% 纵Y%`,
  pass ? RESULTS.PASS : RESULTS.WARNING,     // ← 超限只返回 WARNING，永远不 FAIL
  { lateralOffset, longitudinalOffset });
```

而 `status` 的推导是 `failCount ? FAIL : (warningCount || reviewCount) ? WARNING : PASS`。

**后果链**：重心超标 → 只算 WARNING → status 最多是 WARNING → **不阻断封柜与出运**，评分只扣 7 分（`warningPenalty`），最终显示 **"93 分"**。

**实证**：`backend/result-p5.txt` 的"方案5 家具混装 40HQ"实测 **横向偏移 10.17%**——是 5% 限制的**两倍**，在该方案里被当作正常结果输出。

**这是原则性安全缺陷。** 货代场景里重心横向超标是导致船舶倾斜、集装箱堆垛失稳的直接原因，它必须是 FAIL（硬阻断），不能是建议项。

### A2　专用安全引擎是死代码，从未接线

`backend/services/NingboPortSafetyEngine.js`（v25.0.0-zero-gap-steel-wall）里有完整的：
- 重心横向 ≤5% / 纵向 ≤10%，并带 **CRITICAL 分级**（横向 10%、纵向 15%）
- 载重 28000kg（100% 警告 / 105% 严重）
- 重货压轻货压力校验（`PRESSURE_WARNING_THRESHOLD = 0.5 kg/mm²`）

**全仓引用它的文件只有它自己的两个测试文件**：

```
./__tests__/integration/v25-zero-gap-steel-wall-integration.test.js
./__tests__/unit/NingboPortSafetyEngine-v25.test.js
```

没有任何 route 或 service 引用它。**整套"宁波港安全合规"在运行时从未执行**，只有测试在跑。

同类死代码还有（被引用文件数 = 0，排除自身）：
- `ShippingTimePackingEngine`
- `Realistic4DPackingEngine-v33.0-FINAL`（名字带 FINAL，却完全没接线）

### A3　没有垂向（Y 向）重心约束

`backend/config/compliancePolicy.js`：

```js
cog: Object.freeze({ lateralWarningPercent: 5, longitudinalWarningPercent: 10 })
```

只有横向和纵向。`NingboPortSafetyEngine` 同样只有这两个维度。

`NingboPortComplianceChecker.js:147` 计算了 `cogY` 并输出 `heightRatio`，但**只打印，不判定**。

**集装箱堆垛重心高度直接决定船舶稳性（GM 高度）**。装成"上重下轻"的高重心箱子，是海事事故的经典成因。这一维度在当前系统里**完全缺失**。

### A4　重货阈值定义错误（两处同源）

```js
// NingboPortSafetyEngine.js:35
this.HEAVY_CARGO_THRESHOLD = 20;      // kg (≥20kg is heavy)

// domain/cargo/cargo.js:97
heavy: input.heavy === true || weight >= 20,

// domain/cargo/scenarioTemplates.js:17
heavy: extra.heavy || weight >= 20,
```

20kg 是"单人搬运舒适上限"的参考值，**不是"重货"**。重货应按**积载密度**（kg/m³）或**是否必须机械作业**判定。后果：22kg 服务器主机、35kg 洗衣机与 208kg 设备模块在 `planProjectionModel.js:10` 里被打上同级别的风险标记。

### A5　性能严重超标：超目标 345–1500 倍

`backend/result-p2.txt` / `result-p5.txt` 记录（Node 自身打印的性能警告）：

| 案例 | 件数 | 目标 | 实测耗时 | 超标倍数 |
|---|---:|---|---:|---:|
| 方案5 家具混装 40HQ | 725 | <200ms | **68,998 ms** | **345×** |
| 方案2 多港口拼箱 40GP | 1280 | <200ms | **300,330 ms** | **1500×** |

1280 件要等 5 分钟。真实货代日均几十票，这个耗时不可用。

### A6　装载失败率高，但结果仍被当作"成功"

| 案例 | 理论利用率 | 实际装入 | 实际利用率 | 未装入 |
|---|---:|---|---:|---|
| 方案2（40GP） | 84.0% | **1144 / 1280（89.4%）** | 73.74% | **136 件** |
| 方案5（40HQ） | 75.5% | **710 / 725（97.9%）** | 62.33% | **15 件** |

方案2 有 **10.6% 的货装不进去**。理论利用率 84% 是"假设全部装入"的上限，实际只有 73.74%。这个差距在界面上如果只展示"利用率"，会误导客户。

### A7　求解引擎堆叠：8+ 套并存，无权威

`services/` 下同时存在：
`PackingEngine`、`OptimizedPackingEngine`、`LayeredPackingEngine`、`MaximalRectanglesEngine`、`FastBlockPackingEngine`、`DBLFPackingEngine-v26.2`、`HybridConstraintPackingSolverV2/V23/V24/V25`、`Realistic4DPackingEngine`、`ShippingTimePackingEngine`

实际接线（`AlgorithmOrchestrator.js`）：主 = V25，回退 = V23 → V2 → FastBlock。其余多为死代码或仅被基准测试引用。

维护面已失控：改一处行为要确认 8 套引擎的差异，且"官方求解器"到底是哪个在文档间不一致（见 A8）。

### A8　策略配置自相矛盾

`backend/config/solverPolicy.js`：

```js
officialSolver: 'hybrid-v2.5',
benchmarkProfile: { ..., promotionDecision: 'PROMOTE_HYBRID_V2_3' }
```

声明 V2.5 为官方求解器，但基准的晋级结论写的是 "PROMOTE_HYBRID_V2_3"。同一份配置文件里两个结论打架。

## 第二部分　视觉缺陷（视觉设计师视角）

### V1【最直接】雾把远景吃掉了 —— "远看很糊"

实测相机与雾参数：

```
camera.fov = 34    near = 0.076    far = 114.9
controls.minDistance = 1.2    maxDistance = 38    （可拉到 38 米）
scene.fog = #dce3e6, near = 18, far = 48
scene.background = #dce3e6
```

**相机允许拉到 38 米，而雾从 18 米开始、48 米全雾。**

实测截图 `21-dist-far.png`：拉到最远时，整个集装箱 + 42 件货物**糊成一团灰块**，颜色完全丢失，只剩背景雾色 `#dce3e6` 里一个 3% 大小的模糊体，还飘着一个与物体脱离的标签。

**这是"远看很糊"的第一主因**，且修起来极简单（改雾的 near/far 或限制 maxDistance）。

### V2【已排除假阳性】各向异性过滤在主体材质上失效

实测（`cargo-material-audit.json`）同一场景内 anisotropy 取值：

| 材质 | 用途 | anisotropy |
|---|---|---|
| `pc_cardboard.001` | **纸箱主表面** | **1** ← 失效 |
| `pc_wood` | **木箱主表面** | **1** ← 失效 |
| `pc_tape.001` | 胶带 | 1 |
| `pc_wood_edge` | 木箱边缘 | 8 |
| `pc_cardboard` | 托盘纸箱主面 | 8 |
| `pc_dark_steel` / `pc_steel` | 钢件 | 8 |

**关键判定**：同一场景里 8 是可达的（软件渲染器上限不会只限制部分材质），所以 **anisotropy = 1 是真实缺陷，不是渲染环境假阳性**。

`inspectionMaterials.js:32` 明确设了 `texture.anisotropy = 8`，但主体材质实测为 1 —— 说明该设置在材质 `clone()` 或几何合并过程中丢失。

**各向异性过滤失效的直接表现**：斜视角（俯视箱顶、斜看箱壁）下纹理被过度模糊。这正好是数字孪生最常用的观察角度。

### V3　材质被"拍平"：没有高光变化、没有表面细节 —— "粘在一起、没有高级感"

`scene/inspectionMaterials.js` 的 `finishInspectionMaterial()` 会**硬覆盖 GLB 作者设定的参数**：

```js
if (wood)  { material.roughness = .84; material.metalness = 0; }   // 全覆盖
if (paper) { material.roughness = .94; material.metalness = 0; }   // 全覆盖
material.envMapIntensity = .8;                                      // 全覆盖
material.bumpMap = surface.bumpMap;
material.bumpScale = wood ? .007 : paper ? .0018 : .0008;           // 不可见的量级
```

实测各材质最终值：

| 材质 | roughness | metalness | bumpScale | envMapIntensity |
|---|---:|---:|---:|---:|
| `pc_cardboard.001` / `pc_cardboard` | **0.94**（硬覆盖） | 0 | **0.0018** | 0.8 |
| `pc_wood` / `pc_wood_edge` | **0.84**（硬覆盖） | 0 | **0.007** | 0.8 |
| `pc_steel` | 0.36 | 0.72 | 0.0008 | 0.8 |
| `pc_tape.001` / `pc_tape` | 0.84 / **0.47**（同名不同值） | 0 | — | 0.8 |

**后果**：
- 所有纸箱 roughness 都是同一个常量 0.94 → **没有高光变化** → 表面像纸板贴图，不像有体积的箱子
- `bumpScale 0.0018–0.007` 比可见阈值小两个数量级 → **凹凸完全不可见**
- 木箱 metalness 归 0、roughness 0.84 → 木头看起来像哑光塑料

### V4　法线贴图不可用 + 同型货物零差异

`applyCargoKitGeometries()` 在合并几何时显式剥离属性：

```js
for (const key of Object.keys(geometry.attributes))
  if (!['position', 'normal', 'uv'].includes(key)) geometry.deleteAttribute(key);
```

实测所有货物网格：**`tangents = false`、`uv2 = false`**。没有 tangent，three.js 无法正确应用法线贴图（`normalMap = no` 全部）。

同时实测：36 个纸箱**共用同一个材质实例**，贴图 `repeat = [1,1]`、无 per-instance 变化、无顶点色（`vertexColors = false`）。

**后果**：36 个纸箱的纹理完全相同、朝向相同、无随机扰动 → 视觉上**融合成一整块**。这就是"所有货物粘在一起"的机制。

顶视特写 `25-topview-crop.png` 可直接看到：相邻纸箱之间**没有任何接触暗部/缝隙**，纸箱与木箱都是同一张扁平贴图，无木纹、无高光。

### V5　统计口径旁证

```
instancedMesh = 524    其他 mesh = 754    唯一材质总数 = 1204
```

一个纸箱由 5 个材质组成（`pc_cardboard.001` + `pc_wood_edge` + `pc_ink.001` + `pc_tape.001` + `pc_label.002`）→ 每种包装要 5 个 InstancedMesh 分桶 → 5 次材质状态切换。材质总数 1204 是 draw call 与状态切换的主要来源之一。

## 第三部分　修正后的优先级

上一轮我给的 P0 是"光照校正 + 补批处理 + 相机构图"。补漏后**排序必须改**：

| 新优先级 | 项目 | 类型 | 理由 |
|---|---|---|---|
| **P0-1** | **A1 重心超标改硬阻断（FAIL）** | 算法 | 原则性安全缺陷，可能输出不安全方案；改动小 |
| **P0-2** | **V1 修雾与相机距离（`Fog(18,48)` + `maxDistance 38`）** | 视觉 | "远看糊"的第一主因，改 2 个数字 |
| **P0-3** | **V2 修复主体材质 anisotropy 丢失** | 视觉 | 已排除假阳性的真实缺陷，影响所有斜视角观感 |
| P0-4 | V3 停止硬覆盖 roughness/metalness，恢复 GLB 作者值；bumpScale 提到可见量级 | 视觉 | "没有高级感"的直接原因 |
| P0-5 | 补容器/工人/地牛静态合并（上轮结论） | 性能 | 期望 937 → ≤450 draw call |
| P1-1 | A3 增加垂向重心约束 | 算法 | 缺失的安全维度 |
| P1-2 | A4 重货阈值改积载密度/需机械 | 算法 | 两处同源错误 |
| P1-3 | V4 给同型货物加 per-instance 变化（顶点色/UV 偏移/随机旋转） | 视觉 | 解决"粘在一起" |
| P1-4 | A5 性能：725 件 69 秒必须优化 | 算法 | 商用不可用 |
| P1-5 | A6 界面如实区分"理论利用率"与"实际利用率 + 未装入件数" | 算法/产品 | 避免误导 |
| P2 | A2 死代码清理（含 `Realistic4DPackingEngine-v33.0-FINAL`）、A7 引擎收敛、A8 文档口径统一 | 工程卫生 | 降维护成本 |
| P2 | 光照校正（上轮的 P0-A） | 视觉 | **降级**——实测画面已可接受，不是当前主要矛盾 |

## 第四部分　方法论修正

**上一轮我说"四份报告没打开过项目"，但这一轮我自己也犯了同类错误**：只跑了渲染探针，没跑算法探针；只看了总览机位，没看远景与特写。

**必须固化的两条**：

1. **视觉结论必须跨机位取证**：至少覆盖「远景 / 总览 / 特写 / 顶视 / 斜视」五个机位。只看一个机位会得出相反结论——我在总览看到的是"产品级"，拉到远景才看到"糊成一团"。
2. **算法结论必须读基准输出与配置，而不是读代码结构**：`result-p2.txt` / `result-p5.txt` 里那两行耗时警告（68998ms / 300258ms）和"实际装入 1144/1280"是我上一轮完全没看的东西，而它们比任何代码审查都直接。
