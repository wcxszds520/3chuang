> 评审人立场：项目总设计师（工程纪律 × 产品决策 × 赛程对齐）
> **本轮未执行该方案，仅做只读验证与判断。**

## 摘要

对方这份方案**在工程防错纪律上强于我此前所有输出**，它逐条设闸拦住了我犯过的错（造规则、测错目录、不同条件比较）。

但它有**三个结构性缺口**：不解决"到底改什么"、不对齐截止日期与评分维度、把"产品演示选场景"和"solver 特判"混为一谈。

**我另外交付了一个它没有的东西**：它只把「212」当作排查线索，**我定位到了最小可复现条件**——一个业务字段 `eta` 会改变几何求解结果，装载率从 212 掉到 160（-19.3%）。

## 第二部分　它的三个结构性缺口

### 缺口一：A 包有"空转"风险 —— 它不解决"到底改什么"

A 包的完成标准是"落实一个被复现的执行问题：**失效总预算、错误入口、错误截断、缓存误命中、晚来结果覆盖有效解，或其他真实缺陷**"。

**问题**：如果测量发现预算机制是好的、入口是对的、缓存没问题，A 包就只能交"测量与阻断"。

而 C 包（搜索结构改造）的五条，书写方式全是"**检查** XXX"——检查候选是否只剩大块、检查空间上限、检查分层检查位置。**它把"改什么"的决定权推给了测量结果，但没有预设测量可能得不出结论。**

**并且没有为"空转"设计出口**：如果 A 包发现的问题不是执行缺陷而是搜索质量问题，方案没有说下一步怎么走。这是**防御性极强、推进性偏弱**的方案结构。

**我的补充**：给 A 包加一条**并行支线**——在锁定路径的同时，直接对"已知装载率偏低"的实例做分层计时（normalize / 候选生成 / 空间更新 / search / repair / validate / serialize），**用耗时分布反推瓶颈在哪一层**，而不只是等"找缺陷"。这样即使没有执行缺陷，也能产出"下一步该改哪一层"的结论。

### 缺口二：把"产品演示选场景"和"solver 特判"混为一谈

它在 D 包写：

> "若候选只在某类问题更好，可按真实 problem features/capabilities 路由；**不得按 dataset name、case ID、212/69 或 Hero 名称特判**。"

**前半句对，后半句需要对**——这是**求解器内路由**的规则：禁止按数据集名特判（对）。

**但它把另一件事也一起禁掉了**：**产品演示时选择展示哪个场景**。这是**产品决策**，不是算法特判。选 `smallBatch`（100% 装入、1.1s）而不是 `largeBatch`（跑不完）做演示，是合理的产品行为。

**两者不矛盾**，混在一起会导致"演示安全区"这个低成本高收益的动作被误伤。**正确的区分是**：

| 层面 | 规则 |
|---|---|
| 求解器内部路由 | **禁止**按 dataset name / case ID 特判 |
| 产品演示与截图选场景 | **允许**，且应当做 —— 但要**如实标注**该场景的规模与条件 |
| 对外结论 | 不得用一个场景的结果代表全部场景 |

### 缺口三（最重要）：不对齐截止日期与评分维度

**这是它整份方案完全没有触及的维度。**

时间事实：CMIT 上届时间线是 **9/21 报名截止 → 9/22-26 校赛 → 9/27-10/10 赛区赛**。**今天是 9/18。**

评分事实：赛区 100 分 = 选题策划 20 + **视觉效果 30** + **互动体验 30** + 作品说明 10 + 现场演示 10。**算法不直接计分。**

它规划的 A→B→C→D→E 五工作包，含"重构搜索与预算""四格挑战实验""受控替换 + 浏览器逐件核对"，**且明确要求"不得在最终校验未完成时返回正式成功"、"新实现通过同质量门槛后才启用默认"**。

**这套要求在工程上完全正确，但在 9 天窗口内不可能完成且不引入回归。**

**作为总设计师，我必须说的判断**：如果在赛区提交前执行完整的 A–E，等于**把 60 分的主战场（视觉 + 互动）让出去，去修一个 0 分项**。而且如果 A 包改了求解器、E 包还没验证完就截稿，**风险是演示崩掉**——那是"现场演示 10 分"的直接损失。

**正确的时间对齐应该是**：现在只做 A 包的"锁定路径 + 受控运行 + 修已复现缺陷"，**C/D/E 推迟到赛区提交之后**。这个裁剪不影响它的方法论（哪些该做、按什么顺序），只影响**本轮的范围**。

## 第三部分　我交付它没有的东西：`eta` 字段缺陷

它把 `mediumBatch` 的 212 写成"巧合线索"，要求"查是否有截断、缓存或默认任务污染"，并强调"**不能预设存在硬编码**"。

**我按它的纪律做了**——先提了三个假设，**全部被我自己否掉**：

| 我的假设 | 验证 | 结果 |
|---|---|---|
| `ResultCache` key 未含货物内容导致误命中 | 读源码 | ❌ **否**。`ResultCache` 是按 `taskId` 存的 **AI 合规异步任务缓存**，不是装箱结果缓存 |
| 同一进程内重复求解有状态泄漏 | 同进程连跑 3 次 | ❌ **否**。稳定 212/270 |
| 前序调用（先跑 40HQ）污染后续 | 先 40HQ 再 20GP | ❌ **否**。仍 212/270 |

**然后我改了排查方向：对比我自己两个 harness 的差异**，发现其中一个多带了 `eta` 字段。最小化复现：

| `eta` 取值 | mediumBatch/20GP 装入 |
|---|---|
| 无该字段 | **212 / 270** |
| `null` | **212 / 270** |
| `''`（空串） | **212 / 270** |
| **`"2026-04-15"`（真实日期）** | **160 / 270（-19.3%）** |

模板中实际值为 `["2026-04-15","2026-04-20","2026-04-25"]` —— **三个批次日期**。

**结论：一个业务元数据字段（预计到达时间）泄露进了几何求解链，触发分批/时序逻辑，使装载率从 78.5% 掉到 59.3%。**

**三条推论**：
1. **生产环境的真实装载率是 160 量级，不是 212。** 前端数据模型里货物**带 eta**（`demo-cargo-templates.js`、`initialDataset.js` 均有），所以真实请求必然触发。
2. **我此前所有"212"相关数字都是剥掉业务字段后的实验室结果**，与此前测得的 137/600 等数字**不同条件**，不可混用比较。
3. **这属于对方列举的五类缺陷之外的第六类**：不是预算、入口、截断、缓存或覆盖，而是**"不影响可行性的属性不应影响结果"被违反** —— 恰好是它自己在缓存章节写的原则（"聚合 SKU 必须包含所有影响可行性的属性"）的**反向应用**。

**这个缺陷完全落在它的工作包 A 范围内，且满足它"先建立失败测试再修改代码"的要求** —— 最小复现已具备，可以直接写成断言。

## 第五部分　我的最终判断

### 5.1 技术上：采纳它的纪律，裁剪它的范围

| 层面 | 我的判断 |
|---|---|
| **工程规范** | **完全采纳** —— 分阶段状态、独立 validator、censored 报告、按 rule profile 隔离缓存、聚合 SKU 属性完整性、反特判路由、LLM 不进运行时 |
| **本轮范围** | **裁剪到 A 包的"锁定路径 + 受控运行 + 修 eta 缺陷"**，2–3 天 |
| **C/D/E 包** | **推迟到赛区提交之后** —— 不是否定它的价值，是不与截止日期对撞 |
| **B 包** | 只做"为 eta 缺陷写失败测试"这一小块（它本来就要求 A 包建立最小反例） |
| **PackingSolver 外部对照** | 本轮不做 |
| **DeepSeek 接入** | 可用，但**先实测一次最小 API 调用确认模型名**；且本轮由我（当前会话）直接执行，不另起四代理 |

### 5.2 顺序上：算法排在视觉与互动之后

CMIT 赛区 100 分里算法 0 分。本次只做"不让演示崩 + 让答辩讲得出技术性"这两件。视觉 30 + 互动 30 才是主战场。

### 5.3 我能不能应对好这家大厂的设计师

**诚实回答：在工程防错纪律上，这一轮我输它。** 它的边界设定比我干净——我造过规则、测错目录、不同条件比较后宣称击败，它逐条设了闸。这一点我不辩解。

**但它有三个维度没覆盖，而这三个恰好是我作为项目总设计师该管的**：
1. **结果对齐**（赛程、评分维度、演示风险）—— 它只管技术正确，不管这个时间点该不该做
2. **机制定位**（它给线索，我给最小复现条件和机制）
3. **边界区分**（产品决策 vs 算法特判，它混为一谈）

**所以我的结论是**：**它的方案应当被采纳为工程规范，但不应当在现在、以完整范围执行。** 把它的纪律 + 我的范围判断 + 我定位的 eta 缺陷三者合并，才是这一轮真正该做的事。
