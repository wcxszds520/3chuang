# 甬柜易算 Web 当前态产品设计审计

审计日期：2026-07-10  
审计视口：1672 × 941，同时抽查 1280 × 720  
审计对象：`web-dashboard` 六个业务页面与现有 Three.js 场景  
证据目录：`docs/design_audit_current/`

## 总结

当前实现已经具备浅色物流 SaaS 的基础外观、真实业务数据链路和六页可操作流程，但尚未达到“演示级高质量产品”的完整标准。最大问题不是缺少功能，而是后续迭代叠加了多个视觉范式：高保真业务工作台、V9 系统总控台、真实数据联调态和旧 Round 2 样式同时存在。结果是首页偏离业务主路径、CSS 覆盖关系失控、首屏高度利用不稳定，3D 页虽有真实场景，却没有形成清晰的作业叙事。

当前综合评分：**7.6 / 10**。可以演示功能，不建议按当前画面直接录制最终答辩视频。

## 关键发现

### P0：工作台入口偏离真实用户任务

默认首页当前渲染 `DashboardConsoleV9`，标题是“智能装箱主控台”，主信息为数据库全局统计、`packing_plan` 表、接口路径和外部接口状态。这套信息更像内部运维台，不是中小卖家、配载员、仓库人员和港前审核员的订单决策入口，也明显偏离 `docs/design_refs/dashboard.png` 的“当前订单 + 流程 + 方案 + 风险 + 下一步”。

修复方向：恢复订单任务型首页，以当前订单为唯一主线；全局数据库统计不进入首屏，若保留只能放在开发诊断区且默认隐藏。

### P0：3D 首屏没有完整讲清“当前在做什么”

Three.js canvas 非空且使用真实 `loadedCargo`，但当前镜头过近，集装箱下沿、路径和作业实体被裁切。HUD、约束条、场景标注和右侧作业指令虽然都存在，却因为首屏高度和相机 framing 不协调而彼此竞争。当前画面更像调试器，而不是可播放、可执行、可复核的现场作业孪生。

修复方向：采用“容器主体 70% + 门端作业区 20% + 环境 10%”的镜头构图；用容器包围盒计算总览相机距离；首屏固定完成标题、摘要、3D 舞台和右侧作业单的闭环；保留 InstancedMesh 与既有数据结构。

### P1：样式架构已经失控

`App.jsx` 约 5426 行，`App.css` 约 6039 行，`restore.css` 约 2694 行。相同组件在多个文件和多个轮次重复定义，存在 1280、1320、1360 等相邻断点互相覆盖。`designTokens.css` 还存在重复变量、无效颜色值和负字距。继续追加覆盖会让视觉回归越来越难定位。

修复方向：不做一次性重写；新增最终产品样式入口，先收敛 token 和壳层，再按页面迁移。每迁移一页即删除该页对应的旧覆盖块，避免继续堆叠。

### P1：真实数据一致，但“数据来源状态”表达不够明确

六页当前会话值基本一致为 221/221、84.51%、本地规则 WARNING / AI建议 PASS / 人工复核独立；首页又同时展示数据库最新任务 221/221 和全局统计。用户会误以为是同一订单发生冲突。侧栏显示“本地孪生预演”，但顶部与页面摘要未明确区分“当前会话预演结果”和“真实后端方案”。

修复方向：所有业务页只显示当前会话方案；顶部加入紧凑来源标签 `本地预演` / `后端方案` / `AI 审计`，不把数据库全局任务混入当前订单。

### P1：首屏密度不稳定

货物录入、柜型推荐、合规预审和报告页在 1672 宽度下基本成立，但表格右列裁切、首屏下半部空洞或右侧信息被截断。1280 宽度时三栏直接堆为单列，用户在演示中只能看到表单或局部 3D，主路径消失。

修复方向：1672 采用 3 栏；1280 采用 2 栏而非全堆叠；低于 960 再进入单列。表格区使用最小列宽和横向滚动，不能裁掉状态和操作列。

## 分页审计

### 1. 工作台

优点：壳层清楚、当前会话与真实接口都有数据、卡片风格克制。  
问题：页面主视觉是全局数据库概览；接口路径和表名进入用户界面；能力卡和队列在首屏下方不可见；没有订单四步流程、当前方案缩略、风险摘要和明确下一步。  
结论：**不通过最终录屏门禁**。

### 2. 货物录入

优点：三栏业务结构清楚，表单、SKU、VLM、AI 体检已经形成完整工作台。  
问题：订单摘要仍使用装箱结果而不是数据完整度；SKU 表格末列被裁；缺少搜索、筛选、分页和批量选择；空白区域过大。  
结论：通过结构门禁，需做密度和表格精修。

### 3. 柜型推荐

优点：40HQ 主卡、对比区和 AI 推荐理由主次基本正确。  
问题：CAD 预估图仍是规则矩形，不足以体现真实装箱结果；左栏信息重复；中间主卡下半部分在首屏之外；真实结果未装入 420 件时，“推荐 40HQ”仍需更清楚解释决策边界。  
结论：通过结构门禁，需强化真实结果预览和决策解释。

### 4. 3D 作业孪生

优点：真实 canvas、视角切换、播放、作业实体、路径、目标位、分区、重心和算法依据均已实现。  
问题：相机过近；容器与环境比例失衡；场景标注使用绝对 CSS，旋转后可能与真实 3D 位置脱节；首屏只看到场景上半部；右侧队列和图层在首屏无法完整呈现；重心阈值文案被截断。  
结论：**不通过最终录屏门禁，是第一优先级重构页**。

### 5. 合规预审

优点：评分环、矩阵、RAG、证据预览和人工复核已具备真实审核台形态。  
问题：本地规则、联网参考、AI 解释和人工复核的层级仍过于拥挤；86 分 WARNING 与真实 DeepSeek 审计状态需要在同一页明确区分；整改建议和复核流程没有在首屏形成闭环。  
结论：通过结构门禁，需强化“规则事实 / AI 解释 / 人工结论”三层。

### 6. 报告导出

优点：主视觉已经是报告封面，真实 HTML / CSV / JSON 能力与页面方向一致。  
问题：封面章节仍偏文字卡片，缺少真实方案缩略和矩阵摘要；导出阻断状态占据过大视觉权重；左、右两栏信息密度不平衡。  
结论：通过结构门禁，需做最终交付感和信息平衡精修。

## 可见无障碍风险

- 蓝色小号英文 overline 在浅网格背景上的对比度偏弱。
- 部分 11px 文本和状态标签不适合腾讯会议压缩后的远距离阅读。
- 表格右侧裁切会隐藏状态和操作，属于可见操作性风险。
- 3D 标签使用绝对位置，缩放和视角切换后可能失去语义对应。
- 仅凭截图不能证明键盘顺序、焦点可见性和屏幕阅读器语义；这些需在实现阶段用浏览器交互另测。

## 审计结论

建议采用“受控模块化重构”，先恢复任务型首页和稳定壳层，再集中重构 3D 页面，然后收敛其余四页。禁止继续通过在 `restore.css` 尾部追加大段覆盖来修补。新的设计必须以真实当前会话数据为唯一事实源，并在 1672 × 941 首屏完成每页的主要业务闭环。
